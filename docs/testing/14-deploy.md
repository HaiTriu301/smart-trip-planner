## A. Image của backend và cấu hình bản chạy thật

## B. Image của frontend và nginx

> **Yêu cầu:** design.md 6.3 (IP thật của người gọi), 17.1 (Dockerfile frontend), 17.4 (nginx); WORKFLOW Task 4.8 quyết định 6, 12, 18 · **Kiểm bởi:** bài thủ công `MT-DEPLOY-04` đến `07` (không có test tự động: cấu hình nginx chỉ kiểm được bằng cách chạy nginx thật)

Image frontend chứa trang React đã build sẵn và nginx, chương trình đứng ở cửa của máy chủ. nginx làm bốn việc: trả trang React cho trình duyệt; chuyển mọi lời gọi `/api/...` và Swagger sang backend; nói chuyện bằng HTTPS (chứng chỉ của Cloudflare, khi thử trên máy mình thì dùng chứng chỉ tự ký); và tìm ra **địa chỉ thật của người dùng** rồi báo cho backend, để giới hạn số lần gọi (Task 4.7) đếm đúng người. nginx chỉ tin địa chỉ do Cloudflare báo khi request thật sự đến từ máy của Cloudflare; ai tự gửi header giả thì vẫn bị tính theo địa chỉ thật của họ. Cổng 80 (HTTP thường) không mở: Cloudflare tự chuyển `http://` sang `https://`.

Trình duyệt được phép giữ lại file một cách hợp lý: file JavaScript / CSS có mã trong tên (`index-hmfE6crP.js`) nên được giữ một năm, còn `index.html` luôn được tải lại, nhờ vậy bản mới hiện ra ngay ở lần mở trang tiếp theo.

## C. Cả hệ thống bằng Docker Compose

> **Yêu cầu:** design.md 17.3 (biến môi trường của bản thật), 17.4 (compose prod, RAM); WORKFLOW Task 4.8 quyết định 2, 11, 12, 15, 18 · **Kiểm bởi:** bài thủ công `MT-DEPLOY-08` đến `11` (file compose chỉ kiểm được bằng cách chạy Docker thật)

Một file `docker-compose.prod.yml` dựng cả bốn phần của bản chạy thật bằng một lệnh, thay cho các lệnh `docker network` và `docker run` gõ tay ở phần A, B. Thứ tự khởi động do file quyết định: MySQL và Redis báo "khoẻ" rồi backend mới chạy; nginx chạy ngay, nên lúc backend khởi động lại trang web vẫn hiện, chỉ các thao tác cần máy chủ báo lỗi trong khoảng 20 giây. Chỉ nginx mở cổng (443) ra ngoài máy; backend, MySQL, Redis chỉ nói chuyện với nhau trong mạng riêng của Docker. Mỗi phần có giới hạn RAM (backend 1 GB, MySQL 512 MB, Redis 128 MB, nginx 64 MB: tổng vừa máy 2 GB), tự chạy lại khi bị tắt đột ngột hoặc máy khởi động lại, và giữ log tối đa 30 MB.

Giá trị bí mật nằm trong file `.env` cạnh file compose, chỉ có trên máy chủ. Repo chỉ có file mẫu `.env.prod.example` (tên biến, không có giá trị thật); thiếu một giá trị thì compose dừng ngay và nói thiếu biến nào. ## D. Sao lưu database

> **Yêu cầu:** design.md 17.4 (dòng "Dữ liệu"); WORKFLOW Task 4.8 quyết định 8, 13, 18 · **Kiểm bởi:** bài thủ công `MT-DEPLOY-12` đến `14` (script chạy với Docker thật)

## E. GitHub tự kiểm mỗi pull request

> **Yêu cầu:** design.md 17.2 (`ci.yml`); WORKFLOW Task 4.8 quyết định 5, 18 · **Kiểm bởi:** bài thủ công `MT-DEPLOY-15` đến `17` (workflow chỉ chạy được trên GitHub)

Mỗi khi có pull request (PR), GitHub mượn hai máy Linux sạch và chạy đúng những lệnh mà người làm vẫn chạy trên máy mình trước khi commit: backend `./gradlew build` (biên dịch, toàn bộ test, kể cả test dùng MySQL / Redis thật qua Testcontainers, đóng gói); frontend `npm ci`, `npm run lint`, `npm run build`, `npm run test`. Kết quả hiện ngay trên trang PR: dấu xanh là sẵn sàng merge, dấu đỏ là chưa. Vì máy sạch, CI bắt được cả lỗi "chạy được trên máy tôi" (thiếu file chưa commit, phụ thuộc vào cấu hình riêng của máy).

Thư viện tải về được giữ lại giữa các lần chạy (cache), nên lần sau nhanh hơn. Đẩy thêm commit vào cùng PR thì lần chạy cũ đang dở bị huỷ, chỉ commit mới nhất được kiểm. Test backend đỏ thì báo cáo test được đính kèm lần chạy để tải về xem. Workflow chỉ có quyền **đọc** code, không đăng gì đi đâu.

Không dùng `gradle/actions/setup-gradle` như kế hoạch: từ v6, phần cache của nó là mã đóng theo điều khoản riêng của Gradle; chủ dự án chọn cache có sẵn của `actions/setup-java` (mã nguồn mở) ngày 2026-10-21 (design.md 17.2). `backend/gradlew` từng được lưu trong Git **không có quyền chạy** (`100644`, do tạo trên Windows), nên máy Linux của GitHub sẽ báo `Permission denied`; mốc này sửa quyền đó.

## F. GitHub tự build image khi merge vào `main`

> **Yêu cầu:** design.md 17.2 (`images.yml`); WORKFLOW Task 4.8 quyết định 4, 10, 14 · **Kiểm bởi:** bài thủ công `MT-DEPLOY-18` đến `21` (workflow chỉ chạy được trên GitHub)

Máy chủ không phải build gì: nó chỉ tải image về (`docker compose pull`), vì máy 2 GB build Gradle rất chậm và dễ hết bộ nhớ.

Workflow chỉ được đọc code và đăng image của chính repo này.

Image mới đăng lên mặc định là **riêng tư**. Chủ dự án chuyển hai package sang **Public** một lần, để máy chủ tải được mà không cần đăng nhập vào GHCR. Code của repo vốn đã công khai, nên image công khai không lộ thêm gì: image không chứa secret, mọi secret nằm trong file `.env` trên máy chủ.

**Chặng 3: tên miền, Cloudflare, HTTPS** (`aws.md` mục 10). ## H. Deploy qua GitHub sau khi chủ dự án bấm duyệt

> **Yêu cầu:** design.md 17.2; WORKFLOW Task 4.8 quyết định 4, 10, 17 · **Kiểm bởi:** bài thủ công `MT-DEPLOY-38` đến `43` (chạy được trên máy chủ thật và trên GitHub)

Từ mốc này, đưa bản mới lên máy chủ không cần SSH vào gõ lệnh. Sau khi merge vào `main` và GitHub build xong hai image (phần F), một bước **Deploy** hiện trên tab Actions ở trạng thái **chờ duyệt**: chỉ khi chủ dự án bấm **Approve and deploy** thì GitHub mới nối vào máy chủ và chạy script `deploy.sh`. Chủ dự án chọn giờ deploy, vì mỗi lần deploy trang lỗi khoảng 30–60 giây trong lúc backend khởi động lại. Không duyệt thì bản thật giữ nguyên.

Script `deploy.sh` trên máy chủ làm theo thứ tự:
1. Sao lưu database (gọi `backup.sh` của phần D): bản mới có thể đổi cấu trúc database, bản sao lưu là đường lui.
2. Tải image mới từ GHCR, khởi động lại những phần có image mới; MySQL và Redis không bị khởi động lại nếu không đổi.
3. Chờ backend và nginx báo khoẻ, tối đa 3 phút. Không khoẻ thì in 100 dòng log cuối của backend và báo **thất bại**: bước Deploy trên GitHub đỏ, chủ dự án biết ngay.
4. Xoá các image cũ không còn dùng để ổ đĩa không đầy.

Hai lần deploy không chạy chồng lên nhau (script tự khoá). Nhiều lần merge liên tiếp: chỉ lượt mới nhất còn chờ duyệt; image mang nhãn `latest` nên duyệt lượt đó là đưa bản mới nhất lên.

An toàn:
- GitHub dùng một **khoá SSH riêng**, khác khoá quản trị của chủ dự án. Trên máy chủ, khoá này bị giới hạn: đăng nhập bằng nó **chỉ chạy được `deploy.sh`**, không mở được dòng lệnh, không đọc được file nào. Lộ khoá thì kẻ gian cũng chỉ deploy lại được đúng bản đang có trên GHCR.
- Khoá, địa chỉ máy và "dấu vân tay" của máy nằm trong secret của môi trường `production` trên GitHub: chỉ bước Deploy **đã được duyệt** mới đọc được; GitHub không cho ai đọc lại secret, kể cả chủ dự án.
- GitHub kiểm dấu vân tay của máy trước khi nối: không bao giờ gửi lệnh tới một máy giả mạo.
- Bước Deploy không có quyền gì trên repo.

Cổng SSH (22) của máy phải mở cho mọi nơi, vì máy chạy GitHub Actions không có IP cố định. Bù lại máy chỉ nhận đăng nhập bằng khoá (bài `MT-DEPLOY-26`).

Claude đã kiểm file workflow bằng `actionlint` và hai script `deploy.sh`, `backup.sh` bằng `shellcheck` (công cụ kiểm lỗi script shell, chạy trong Docker): không lỗi. Việc chạy thật chỉ xem được trên máy chủ và GitHub.
